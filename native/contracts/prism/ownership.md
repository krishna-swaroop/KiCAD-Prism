## 1. Rules this map adds to ADR §9.1

A WP edits only the paths it owns in its wave. It reads everything else. The "Port from" sources of §9.5 are read-only to the porting WP.

1. **One owner per file per wave.** §4 lists every file that more than one WP needs, with its owner in each wave. Within one wave, no two WPs own the same file unless one stacks on the other (§3).
2. **Owner succession.** Once the owning WP has merged, its shared files pass to the integration agent of the current wave (`INT` below). A WP that needs a change to such a file states the exact change in its PR body. INT applies it as a commit of its own, titled `shared(<path>): <change> for <WP>`, before it stacks the requester. Where a later wave has a named owner, §4 says so.
3. **Hand-over by stub.** When a later WP fills a file that an earlier WP must create, the earlier WP creates a stub and the later WP owns it from then on. This covers the projection modules (F2 → P1–P5), the bundle and CLI crates (F2 → B), the models stage (K → V1) and the Simulation Studio settings group (K → C6).
4. **Reserved number blocks.** Every schema migration uses a version allocated in §5.
5. **Build output is rebuilt, not merged.** `frontend/public/prism-semantic-viewer.js`, the served WASM and the cache-key line of `frontend/index.html` are regenerated by INT after stacking any WP that touched `kicad-prism-viewer/viewer/`.
6. **Agent maps.** A WP creates or edits an `AGENTS.md` only inside a directory it owns. It lists the lines it needs in the root `AGENTS.md` and `backend/app/services/AGENTS.md` in its PR body, and INT applies them once per wave. `scripts/check_agent_docs.py` fails only on paths that no longer exist, so a missing map line never fails a WP; a deleted path does, which is why the Wave 4 WPs that delete mapped modules own the maps (§4).

Path status, as in the JSON: `dev` (the path, or a match of the glob, exists on dev), `ref-only` (exists only on the reference branch, copy-from), `new`. A `new` path under `native/` that arrives with F1's import is marked "from fork" (the fork path exists at `b6316117`, with `prism-kicad-*` read as `kicad-monkey-*`).

Totals: 328 owned path entries across 29 WPs: 198 exist on dev, 11 only on the reference branch, 119 new (15 of them arrive with the fork import). Shared files: 66 (54 dev, 0 ref-only, 12 new).

- **Why the W0 move right after F1.** F2 generates Rust for the W0 schemas, and K's and B's tests read the revision-key vectors from their final place (`native/contracts/prism/revision-key-vectors.json`, proposed in `README.md`, "After WP-F1").
- **Why L right after F2.**
  - L builds `prism-kicad` and copies crate paths into the Dockerfile, and F2 renames every crate.
  - Until L adds a `native` area to `scripts/ci_changes.py`, a PR that touches only `native/**` runs no CI job (`scripts/ci_changes.py:30-57`; the `quality-gate` aggregator passes skipped jobs).
  - F3's and G's CI jobs are added to `dev-quality-gate.yml` by INT once L has merged (§4).
- **Wave 3.** C6 takes a1's new frontend types from C1. C4's System Builder 3D scene renders boards through `kicad-prism-viewer/viewer/` (`prism-semantic-viewer-element.js:268`, `viewer-controllers.js:5`), which C5 rewrites, so C4 is split (maintainer decision): C4a, the System Builder interface, lands in parallel with the other Wave 3 WPs, and C4b, the 3D scene, lands after C5.
- **Wave 4.**
  - R1 deletes the legacy branches first, because R2's removals assume no caller is left.
  - R2 and R3 both edit `backend/Dockerfile` and `dev-quality-gate.yml`, so R3 stacks on R2.
  - R4 drops stores no reader uses after R1.
  - X runs last, because its test passes only when R1, R2 and R4 are in.

## 8. Dependency-order problems (task item 3)

1. **G before F1.** §9.4 gives G only W0 as a dependency, but G owns `native/parity/`, and `git subtree add --prefix=native` fails when `native/` exists. G depends on F1.
2. **F0's `native/LICENSES.md` before F1.** Same cause. F0 signs off before F1; its `native/LICENSES.md` commit lands after F1. The allow-list and excluded-fixture list live in `docs/architecture/native-provenance.md` until then.
3. **The verbatim import fails the definition of done.**
   - If the fork's `AGENTS.md` is on F0's allow-list, `scripts/check_agent_docs.py` fails on it: it names `input/`, `kicad/`, `output/` and `reference_output/` (fork: `AGENTS.md:7-9`), which do not exist even in the fork.
   - `.gitignore:38` hides the 85 fork files tracked under `generated/` directories.
   - F1 adds two commits after the import: one fixes `native/AGENTS.md`, one re-includes the generated directories in `.gitignore`. The checker itself stays unchanged.
4. **L before F2.** L depends on F1 in §9.4, but builds `prism-kicad` and names crate paths that F2 renames. L depends on F2.
5. **P-WPs need generated Rust contracts that nobody generates.** The fork's codegen has a hard-coded schema list (fork: `src/rs/kicad-monkey-codegen/src/main.rs:17`). F2 adds the 19 W0 roots and generates them into `native/src/rs/prism-kicad-contracts/src/generated/prism/` before Wave 2.
6. **`lib.rs` and `divergences.md`.** Parallel P-WPs cannot each own a line of one file (§6).
7. **V1 edits K's job, and two specs disagree on who runs the GLB export.** ADR §9.5 gives V1 the `models` stage; `cli-spec.md` §9.1 says the export is "Run by K" inside the `design_bundle` job. Both hold if K's job calls `design_bundle/stage_models.py`, which K creates as a stub and V1 owns from Wave 2 (§1, rule 3).
8. **B's reader depends on a crate that stays in prism-sim-studio.** sim: `src/prism-bundle/src/reader.rs:9`, `:88-92` use `prism_geometry::Geometry`. ADR §4.1 moves only `prism-bundle`, and §2.8 forbids Prism depending on prism-sim-studio. This is an open question.
9. **R2 is blocked.** See §2, item 5. Until it is decided, R2's acceptance ("`requirements/runtime.in` has no `kicad-monkey`") cannot pass, and neither can X's test for the catalog modules.
10. **Wave 4 is not parallel.**
    - R1 must precede R2, because R2 removes code that R1's deletions make dead.
    - R3 must follow R2 on the shared Docker and CI files.
    - R4 needs R1 (no reader of the old stores remains), and its table drops need a later release (§5).
    - X needs R1, R2 and R4.
11. **C4 needs C5.** System Builder's 3D scene reads the same analytic renderer that C5 ports (`<prism-semantic-viewer mode="system">`).
12. **C6 needs C1's types,** or C6 and C1 would both edit `frontend/src/types/prism-selection.ts`.
13. **K's tests need the W0 move.** The revision-key vectors move from this directory to `native/contracts/prism/`. K stacks after the W0 move, or reads the staging path and updates it in the W0 move.
14. **V1 needs P4** (§2, item 8). V1 stacks after P4 in Wave 2, or keys the GLB cache on every model blob of the revision-key listing instead (open question 11).
15. **Stacked PRs get no CI.** ADR §9.1 allows stacking on another WP's branch, but `dev-quality-gate.yml` runs `pull_request` only for the base branches it lists (open question).

## 11. Field map of `ownership.json`

Its fields follow the field-map template of `conventions.md` §15 so the integration agent, the WP agents and WP-X's test can read it the same way. ### How the map was produced

2. `grep -rn "kicad_monkey" backend/app kicad-prism-viewer scripts` on W, without `node_modules`, gave the import sites and mentions of §10.
3. The callers of every module a consumer WP touches were listed with `grep -rln <module> backend/app` (for example `semantic_index_service`: 10 importers, `interface_extractor`: 14), and every file a W0 field map cites as a consumer was resolved to a path and checked to have an owner in Waves 2–4. 4. A pairwise check over `owns` found no two WPs of one wave owning an overlapping path unless one stacks on the other (`depends`/`mergeAfter`).
