# Release Studio R9: retention pins

R9 makes `ws_artifact_release_pins` an indefinite liveness marker for the
content-addressed artifacts used by Release Studio dossiers, attestations, and
evidence.

## Retention behavior

`JobService.prune_artifact_metadata` excludes every artifact with a pin through
one `NOT EXISTS` predicate covering invalidated, partial, and general terminal
job retention. The predicate is part of the single `DELETE`, so an artifact
cannot be selected by one retention branch while a separate pin check races
with deletion. Pins have no TTL.

An unpinned artifact with otherwise equivalent metadata continues through the
existing retention rules, including `retention_seconds=0`. A pin also wins over
invalidation: the metadata row remains available for later release inspection.

## Filesystem garbage collection

`JobService.referenced_object_paths` returns object paths for both
non-invalidated artifacts and all pinned artifacts. `JobArtifactService` keeps
its existing artifact-root containment and grace-period checks, so the central
liveness set protects a pinned object while old, unpinned siblings are
reclaimed.

R9 does not add pin creation, release APIs, expiry, migrations, or another
artifact catalog.

## Validation

The focused PostgreSQL test uses only the disposable `TEST_POSTGRES_URL` and
skips when that dependency is unavailable:

```sh
TEST_POSTGRES_URL=postgresql://.../release_r9_test \
PRISM_DATABASE_URL= \
python -m unittest tests.test_release_studio_retention -v
```

It covers general, invalid, and partial metadata retention; invalidated pinned
path liveness; and real filesystem GC with `grace_seconds=0`.
